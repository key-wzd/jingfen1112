## 方案可见性

| 创建者 | 谁可以查看/恢复 | 谁可以删除 |
| --- | --- | --- |
| 普通账号 | 创建方案的同一登录账号 | 创建者 |
| 管理员 | 所有已登录账号 | 管理员 |

普通用户的个人方案对其他用户及其他管理员均不可见。管理员可以把共享方案恢复为当前视图；普通用户也可以基于共享方案保存自己的私有副本。

同一账号、同一品类、同名方案会更新；不同账号的同名方案互不覆盖。管理员方案更新由创建该同名方案的账号保存；其他管理员可删除共享方案，或以自己的账号保存新方案。

### 实现

- 服务端在登录会话中记录 accountId（登录用户名），不使用可能重复的显示名称，也不信任浏览器提交的 owner 或 role。
- MySQL 新建 analysis_plans 表，保存创建者、可见范围、品类、方案内容及时间。
- GET /api/analysis-plans?category=...：只返回当前账号可见的方案与服务端确认的身份。
- GET /api/analysis-plans/:id：按身份重新检查读取权限。
- POST /api/analysis-plans：普通账号自动保存为私有，管理员自动保存为共享；校验品类、记录、基准、图例和数据版本。
- DELETE /api/analysis-plans/:id：按创建者/管理员共享维护规则校验。
- 未登录返回 401；不可见的方案 ID 返回 404，避免泄露个人方案是否存在。
- 方案保存在数据库中，同一账号可以跨浏览器或电脑访问。
- 保存内容包含测试对象、基准对象、每行图例显隐状态和数据表版本。
- 旧数据版本的方案暂停恢复，避免重新导入后自增编号复用导致选错记录。方案不复制整套测量数值。
- 选择缓存也按账号隔离，避免同一浏览器切换账号后自动沿用另一账号的选择。
- 旧版 tc-lab-analysis-plans 本地方案没有创建人信息，无法可靠识别归属。本次不自动迁移或发布，需由原创建者重新保存。
- 新旧配置中的共享范围由后端强制决定，篡改 localStorage 角色不能将个人方案发布为共享。

## 多账号配置

默认保留 user 和 admin 本地调试账号。多人共用 user 登录，服务端会将其视为同一个账号；每个人应有不同用户名。

可复制 server/accounts.local.example.json 为 server/accounts.local.json，修改用户名、密码、显示名称与角色后重启 API。此文件已加入 .gitignore。示例中的密码只是占位内容，必须改成实际密码。

也可通过 TC_AUTH_ACCOUNTS_FILE 指定管理员维护的账号配置文件。默认的 user/admin 配置继续使用现有 TC_ANALYST_*、TC_ADMIN_* 环境变量。更成熟的内部部署建议后续接入组织统一身份系统，而非通过共享测试账号区分人员。

## AI 接入可行性

现有 Vue 前端 + Express API + MySQL 可以增加“分析助手”：

```text
用户问题
  → Express 校验登录和方案权限
  → 受控查询/计算工具：当前方案、场景指标、基准差值
  → 模型生成带记录引用的解释
  → 前端展示答案与可点击的数据来源
```

建议第一阶段支持：
- 自然语言筛选，例如“查看这批设备的待机功耗”。
- 解释当前对比差异，引用记录编号、场景、单位、版本。
- 生成内部评审摘要，并列出缺测项与条件不足之处。
- 从有权限的测试规范或报告检索资料，辅助解释。

数值、单位换算和差值由程序计算，模型负责解释。模型工具执行前复用服务端权限；个人方案不能因为 AI 检索而被其他账号读取。初期采用只读工具，导入、删除和修改配置仍由现有界面操作。API 密钥只保存在服务端。

部署可选择云端模型 API 或内网模型。Ollama 官方文档展示了工具调用能力；可用来实现“由模型提出查询、后端执行授权工具、返回结果再解释”的流程。实际模型和硬件选择需要基于内部问题集评测正确率、延迟和资源消耗。

本轮仅实现方案权限与置顶组件；未接入模型、未上传内部数据、未产生模型调用费用。
